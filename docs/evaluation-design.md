# 评估体系设计（对齐稿）

> 本文档从 DESIGN.md 第 6 章抽出并重构，是评估体系的独立对齐文档。**先对齐，后开发。**
> 核心结构：评估 = 两个完全隔离的部分 + 一套插件化机制。

---

## 0. 一页总览

```text
┌──────────────────────────── 生产侧（live）────────────────────────────┐
│ S1 研究 ⇄ S2 档案 ⇄ S3 决策卡                                        │
│      ↑↓ 每轮产出都过【过程评估】                                       │
│   过程评估：评"做得对不对"，产出反馈驱动下一轮 loop                    │
│   数据：最新数据，产出真实投资意见                                     │
└───────────────────────────────────────────────────────────────────────┘
                  ✕ 数据不互通（单向阀：只许聚合报告上行）
┌──────────────────────────── 模拟侧（eval）────────────────────────────┐
│ 独立评估环境：历史时间点回放（研究→档案→决策→前瞻收益）                │
│   效果评估：答"这套系统历史上是否真的有效"                             │
│   数据：真实历史数据 + 时间锁（≤T），eval 命名空间，永不回流生产       │
└───────────────────────────────────────────────────────────────────────┘
```

| | 第一部分：过程评估 | 第二部分：效果评估 |
| --- | --- | --- |
| 评什么 | 研究结论/档案/决策卡的**质量**（做得对不对） | 系统决策的**效果**（历史上赚不赚钱、是否靠穿越） |
| 跑在哪 | 生产循环内，每轮研究/出卡后自动触发 | 独立模拟环境，历史时间点回放 |
| 用什么数据 | **最新数据**（无时间锁），产出真实投资意见 | **真实历史数据 + 时间锁**（只用 ≤T 可知信息） |
| 反馈去向 | 直接进下一轮 loop：gap 清单、打回、补充研究问题 | 聚合评估报告 → 人工/Promotion Gate → 改进方向 |
| 反馈周期 | 分钟~小时级（软闭环，高频） | 天~周级（硬闭环，有预算与审批） |
| 产物 | ProcessReport（维度分 + 缺口 + 建议） | EvaluationReport（签名 artifact，配 manifest） |
| 失败后果 | 打回重做/补充研究（便宜） | 整批作废、holdout 预算扣减（贵） |

---

## 1. 第一部分：过程评估（生产侧，驱动 loop 迭代）

### 1.1 定位

嵌在 S1→S2→S3 生产循环里的"质检线"。每一轮研究结论、每一次档案写入、每一张决策卡产出后，过程评估插件自动运行，输出**反馈**（不是分数排名），直接决定 loop 的下一步：继续下一轮研究 / 打回补充 / 放行出卡。

### 1.2 插件清单（过程评估族）

| 插件 | 挂载点 | 评什么 | 判定类型 |
| --- | --- | --- | --- |
| evidence-binding | S2 落库前 / S3 出卡前 | 每条结论绑证据（来源+原文+时间戳） | **硬门禁**：不过不落库/不出卡 |
| numeric-guard | 任何报告/卡产出前 | 受保护数字与证据原文逐字一致 | **硬门禁** |
| coverage-check | 每轮研究结束 | 档案 schema 完整度 + 事实新鲜度 | 软反馈 → 进 gap 分析 |
| source-independence | 每轮研究结束 | 证据源多样性，防同源复述冒充多方验证 | 软反馈 |
| counter-evidence | 每轮研究结束 | 核心假设是否采集了反对证据 | 软反馈（缺失则自动生成反方研究问题） |
| claim-consistency | S2 落库时 | 新结论与档案现存版本的一致性；冲突→竞争版本+标记 | **硬规则**（不许静默覆盖） |
| risk-review | S3 出卡前 | 失效条件/仓位上限/证据链完整性 | **硬门禁** |
| research-rubric | 每轮研究结束 | LLM-as-judge 按 rubric 评研究报告质量，产出缺口清单 | 软反馈 → 驱动下一轮 |
| thesis-drift | S3 出卡前 | 决策论点与最新档案事实的一致性（档案更新后论点是否过时） | 软反馈 |

### 1.3 反馈环

```text
一轮研究产出 → 过程评估插件组 → ProcessReport
  ├─ 硬门禁失败 → 打回（本轮结论不落库/卡不出具，附失败原因）
  └─ 软反馈 → gap 分析输入 → 生成下一轮研究问题清单
       → 【D3 已确认：milestone 档】自动进入下一轮；仅在扩预算/高风险操作时请示人工
```

**收敛判据**：完整度达标 + 无高危冲突 + 硬门禁全过 + rubric 无关键缺口，或预算耗尽。

## 2. 第二部分：效果评估（模拟侧，独立评估环境）

### 2.1 定位

回答唯一问题：**"这套系统历史上是否真的有效？"** 用真实历史数据，在隔离环境里完整回放"研究→建档→决策→对账"全链路。它评估的对象是整个系统（含过程评估在内的生产逻辑），但运行环境与生产完全隔离。

### 2.2 与生产的隔离机制（五条，缺一不可）

| # | 隔离 | 机制 |
| --- | --- | --- |
| 1 | 数据命名空间 | 生产 KB 与 eval KB 物理分离；eval run 的一切写入打 `eval_run_id`，**永不回流生产库**（单向阀） |
| 2 | 模式 | run manifest 创建时冻结 `mode=live\|eval`，进程级开关，运行中不可切换 |
| 3 | 数据网关 | eval 模式时间锁：只放行 A/B 级 PIT 源，逐条校验 `available_at ≤ T`；通用 web 搜索**禁用** |
| 4 | 权限 | 评估代码/配置/holdout 数据 = protected paths，agent 只读；改进者只读**聚合报告**，读不到 holdout case 细节 |
| 5 | 配置 | 评估配置 = 声明式 mandate 文件（时间点/标的池/基线/阈值/backbone cutoff），冻结哈希 + 签名，改动=新一轮 |

### 2.3 插件清单（效果评估族）

| 族 | 插件 | 作用 |
| --- | --- | --- |
| 回放协议 | walk-forward 调度器 | 决策点序列 T1..Tn 严格按时间推进，Tk 产物不得含 >Tk 信息 |
| | warm-up/eval 两阶段 | warm-up 段建 as_of(T) 档案，评估段禁未来（InvestorBench/FinMem 惯例） |
| 基线 | buy-and-hold / 指数 / 等权 / 动量因子 | 排除"赚钱只是行情好" |
| | **LLM-only 对照** | 无档案无证据裸模型同步决策；诚实指标 = 相对它的超额 |
| 污染检测 | leakage-audit（hook，必达） | 每次模型调用前审计输入投影是否含 >T 信息；**通过率必须 100%，否则整批作废** |
| | canary 诱饵 | 注入假"未来事实"，被引用即判污染作废 |
| | memorization probe | FinLeak-Bench 式 QA 量化每个 backbone 的参数记忆水平（85-93% 是现状），分数随报告出具 |
| | 反事实扰动（PC/CI/IDS） | 扰动输入证据测决策敏感度；决策不变 = 在背答案（P4 阶段实现） |
| 统计对账 | forward-return 对账 + 成本模型（强制 hook） | (T, T+h] 真实行情结算，手续费/滑点不可关闭 |
| | DSR / PSR | 校正多重检验与非正态（Bailey & López de Prado） |
| | generalization gap | dev 区间 − holdout 区间表现差 |
| | median-of-N | 同配置 n≥5 重复取 median（InvestorBench 惯例） |
| | 市场状态分层 | 按趋势/波动率区间分组报告 |

### 2.4 截止日分区（诚实报告的第一前提）

每个 backbone 的知识截止日登记进 manifest，决策点分两种区：

| 区 | 口径 |
| --- | --- |
| 污染区（T ≤ backbone cutoff） | 模型可能背过这段历史 → 结果只作参考，附记忆探测分数，**不得用于"系统有效"的结论** |
| 诚实区（T > cutoff） | 参数记忆天然排除 → 主结论只能出自这里（代价：区间短、样本少） |

### 2.5 holdout 与晋升

最近 12 个月为私有 holdout：评估配置冻结后才可运行，**有查询预算上限**（如 ≤10 次），只报聚合统计。策略/方法论从 dev 进生产关注池走人工 Promotion Gate，agent 无权自动跨越。

## 3. 插件化机制（两部分共用）

所有评估方法实现为统一接口的插件，组合由 profile/mandate 配置决定，新增评估方法 = 加插件，不动主干：

```yaml
EvaluatorPlugin:
  id / version:           # 内容寻址，进 manifest 保证可复现
  scope: process | effect | both
  mount_point:            # 挂载的生命周期点（如 post-research-round / pre-card-issue / eval-replay）
  inputs / outputs:       # typed contract
  verdict: hard_gate | advisory    # 硬门禁 or 软反馈
  cost_estimate:          # token/算力预算预估，审批对话框显示
  config_schema:
```

**跨两部分复用的插件**（scope=both，但数据语境完全不同）：evidence-binding、numeric-guard、claim-consistency——生产过程拿最新数据当质检，效果评估里它们在 ≤T 语境下跑同一套规则。规则同构、数据隔离。
